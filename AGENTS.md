# AGENTS.md — Rules for AI agents

This file is the source of truth for how code is written in this repository.
Follow every rule. If a request conflicts with a rule, say so before writing code.

## 1. Scope

- One repo = one bot = one end-to-end business process. Never add a second process here.
- The process is an ordered list of **tasks** (steps), defined in `process.py`.
- Write everything in English: code, comments, docs, file names.

## 2. Structure

```
main.py            bootstrap: settings -> logging -> engine -> Process.run() -> close engine
process.py         PROCESS_TASKS: the ordered list of task classes
config/settings.py env vars -> frozen Settings dataclass (the only place that reads os.environ)
core/              technical layer, no business knowledge
  engines/         BaseEngine contract + Selenium/Playwright implementations + factory
  base_page.py     BasePage: protected helpers (_click, _fill, ...) over the engine
  base_task.py     BaseTask: run() = retries + timing + logs + screenshots around execute()
  context.py       ProcessContext: the only channel between tasks
  retry.py         generic retry loop (no sleep)
  logger.py        logging setup + log_event() with structured fields
  exceptions.py    BusinessException, SystemException
pages/             one class per web screen
components/        UI pieces reused across screens (tables, menus, modals)
tasks/             one class per process step
services/          integrations outside the browser (Excel, email, DB, APIs)
data/input/        input files      data/output/  generated files
evidence/          screenshots      logs/         log files
tests/             pytest tests for the bot (unit, architecture and e2e)
deploy/            Azure DevOps and Airflow examples
docs/              architecture.drawio (update it when the architecture changes), logo.svg, logo-dark.svg
```

## 3. Layering rules

Dependencies point downwards only:

```
main.py -> process.py -> tasks/ -> pages/ + components/ + services/ -> core/
```

- Only `core/engines/` imports `selenium` or `playwright`.
- Tasks never contain locators. They only call page, component and service methods.
- Tasks never import `core.engines`; they pass `self._engine` to page constructors.
- Pages never call or import other pages, tasks or services, and contain no business logic.
- Pages return data; tasks decide what to do with it (including raising BusinessException).
- Pages and components use the browser only through `BasePage`'s protected helpers.
- Tasks communicate only through `context` (`ProcessContext`), never through globals.
- `process.py` defines the order of tasks. File names are never numbered.
- Only `config/settings.py` reads environment variables. Everything else receives `Settings`.

`tests/test_architecture.py` enforces several of these rules. Never weaken it to make a change pass.

## 4. Naming conventions

| Element   | File                          | Class                   |
|-----------|-------------------------------|-------------------------|
| Page      | `login_page.py`               | `LoginPage`             |
| Component | `results_table_component.py`  | `ResultsTableComponent` |
| Task      | `download_invoices_task.py`   | `DownloadInvoicesTask`  |
| Service   | `excel_service.py`            | `ExcelService`          |

- A task's only public method is `run(context) -> context`, inherited from `BaseTask`. Implement `execute(context) -> None`.
- Methods: verb + object (`fill_username`, `click_login`, `get_invoice_total`).
- Booleans: `is_`, `has_`, `can_` (`is_logged_in`, `has_results`).
- No abbreviations (`start_date`, never `st_dt`). Lists are plural, items singular.
- Constants and locators: `UPPER_SNAKE_CASE`.
- Env vars: prefix `RPA_` (except `OTEL_*`).
- Output files: `<process>_<YYYYMMDD_HHMMSS>.<ext>`.
- Screenshots: `<task>_attempt<n>_<YYYYMMDD_HHMMSS>.png` (generated by `BaseTask`).

### Locators

Declare locators as class-level constants in pages and components, with these prefixes:

`BTN_` button · `TXT_` text input · `LBL_` label/text · `LNK_` link · `CHK_` checkbox ·
`RDO_` radio · `DDL_` dropdown · `TBL_` table · `MDL_` modal · `IFR_` iframe

- Use plain strings. CSS by default: `TXT_USERNAME = "#username"`.
- Use XPath only when CSS cannot express it, with the `xpath=` prefix: `LNK_LOGOUT = "xpath=//a[contains(@href, '/logout')]"`.
- Priority: `id` → `data-testid` → `name` → CSS → relative XPath. **Never use absolute XPath.**
- For dynamic locators, use a `str.format` template constant (see `ResultsTableComponent`).

### Waits

- **Never call `time.sleep()`.** Use the engine's explicit waits (`_wait_for`, or actions that wait implicitly: `_click`, `_fill`, `_get_text`).
- `_is_visible` never waits. Wait for something first, then check.

## 5. Error handling

| Situation | Raise | Behavior |
|---|---|---|
| Timeout, element not found, site down, browser crash | `SystemException` | Retried up to `RPA_MAX_RETRIES` (default 3) |
| Invalid data, record not found, business rule failed | `BusinessException` | Not retried. Stops the process, or skips the task if `STOP_ON_BUSINESS_ERROR = False` |
| Any other exception | (wrapped as `SystemException`) | Retried |

- Engines already raise `SystemException` for technical failures. Do not catch them in tasks or pages.
- Raise `BusinessException` from tasks, with a message a business user understands.
- `BaseTask` saves a screenshot in `evidence/` and writes a structured log entry for every failed attempt. Do not add your own.
- `execute()` must be idempotent: a retry runs it again from the start. Begin by navigating to a known screen.
- `main.py` closes the browser in `finally`. Do not open or close the browser in tasks.

## 6. Logging

- Use `logging.getLogger(__name__)`. Never use `print()`.
- For process/task events, use `core.logger.log_event()` with the fields `process_name`, `task`, `attempt`, `status` (`started|succeeded|failed|retrying`) and `duration_ms`.
- Never log secrets (passwords, tokens). `Settings.password` is hidden from `repr`.
- Do not import OpenTelemetry in the code. It is enabled only from outside (see README).

## 7. Configuration and secrets

- Code reads only environment variables, through `config/settings.py`.
- Every new variable: add a field to `Settings`, read it in `load_settings()`, and document it in `.env.example`.
- Never commit `.env` or real credentials.

## 8. How to add a new screen

1. Create `pages/<screen>_page.py` with class `<Screen>Page(BasePage)`.
2. Add a `URL_PATH` constant if the screen has its own URL.
3. Declare locators as prefixed constants (`BTN_`, `TXT_`, ...), following the locator priority.
4. Add public methods named verb + object that use only the `_click`, `_fill`, `_select`, `_get_text`, `_is_visible`, `_wait_for` and `_open_path` helpers.
5. Return data (`str`, `bool`, lists, dataclasses). Do not raise BusinessException and do not decide flow.
6. If a UI piece appears on several screens, put it in `components/<piece>_component.py` instead.

## 9. How to add a new task

1. Create `tasks/<verb>_<object>_task.py` with class `<Verb><Object>Task(BaseTask)`.
2. Implement `execute(self, context: ProcessContext) -> None`:
   - Build the pages, components and services you need (`LoginPage(self._engine, self._settings.base_url)`).
   - Start from a known screen so retries are safe.
   - Read inputs from `context` and `self._settings`. Write outputs as typed fields on `ProcessContext` (add them in `core/context.py`).
   - Raise `BusinessException` when a business rule fails.
3. Set `STOP_ON_BUSINESS_ERROR = False` only if the process can continue without this task.
4. Add the class to `PROCESS_TASKS` in `process.py`, in the right position.
5. Add tests in `tests/`.

## 10. Definition of done

- [ ] The rules in this file are respected.
- [ ] It runs with both engines (`RPA_ENGINE=selenium` and `RPA_ENGINE=playwright`).
- [ ] There are no `time.sleep()` calls.
- [ ] New env vars are added to `.env.example` (and to `Settings`).
- [ ] Tests pass: `pytest` (offline only: `pytest -m "not e2e"`).
